# MAGIC: Qwen3.6 and Ministral Model Support

[Project README](README.md) · [Model support details](magic_model_support/README.md) · [Training guide](magic_model_support/WORKFLOWS.md) · [中文训练指南](magic_model_support/WORKFLOWS.zh-CN.md)

This versioned guide describes the Qwen3.6 and Ministral support in `magic_model_support/`, including SFT, alternating MAGIC training, checkpoint conversion, and training services.

The model adapters and training launchers build on the contribution by **Dongcheng Zhang ([@Ing1024](https://github.com/Ing1024))** in **[PR #4](https://github.com/AI45Lab/MAGIC/pull/4)**, originally integrated through `integration/qwen36-ministral`. Subsequent updates align the new RL path with the original trainer's attacker format validation and group-level invalid-rewrite reward correction. We thank @Ing1024 for contributing the new model support.

## Supported models

| Model | Training interface | Prepared attacker SFT output | RL deployment |
|---|---|---|---|
| Qwen3.6-27B | Text language model extracted from the `qwen3_5` wrapper; `qwen3_5_text` training configuration | `<think>reasoning</think><answer>rewritten prompt</answer>` | Two hosts: active-policy controller and opponent/Guard services |
| Ministral-3-14B-Reasoning-2512 | Native Mistral3 wrapper and tokenizer, with an independent output head | `[THINK]reasoning[/THINK]rewritten prompt` | One host with separate GPU sets for the active policy and frozen opponent |

These entry points train on text. The Qwen runtime identifiers use `qwen3_5` / `qwen3_5_text` even though the supported checkpoint is Qwen3.6-27B. Ministral preserves its native reasoning format and official reasoning system prompt.

For the original Qwen2.5 and Llama workflows, use the [project README](README.md), the original `scripts/` entry points, and their corresponding environment. The `20260922-qwen2.5-vllm0.8.5` branch preserves that version; `20261015-qwen3.6-mistral-vllm0.18` contains the new model support and subsequent reward fixes.

## Runtime

The new compatibility layer targets the following backend stack:

| Component | Target |
|---|---|
| vLLM | `0.18.0` |
| PyTorch | `2.10` |
| Transformers | Transformers 5 model APIs |
| VERL | `0.10.0.dev0`, revision `5ba5f2f51281522150a6c1c87e3f841d1d220042` |

Use a dedicated Linux/CUDA environment for this stack. The root `requirements.txt` describes the original environment and is not the installation recipe for these launchers. The modern runtime must import the specified VERL revision rather than the repository's vendored `src/verl`.

Transformers 5 is outside vLLM 0.18.0's declared `transformers<5` dependency bound. This combination requires the documented compatibility patches and explicit environment provisioning; the version table alone is not a complete installation lockfile. The Qwen launcher patches a copy of `VERL_SNAPSHOT_SOURCE`; the Ministral launcher patches backend files inside its dedicated environment. See the [runtime guide](magic_model_support/WORKFLOWS.md#runtime).

The launchers restart local Ray processes. Use dedicated hosts, absolute paths, and a unique `RUN_ID` and output directory for each new run.

## SFT entry points

SFT uses a shared native PyTorch FSDP training loop with model-specific loading and tokenization. Prepare JSON arrays containing `instruction`, `input`, `system`, and `output`. Qwen targets use the explicit `<think>` / `<answer>` format; Ministral targets use native `[THINK]` markers and its official reasoning system prompt in the prepared records.

Set the required variables before launching:

| Variables | Purpose |
|---|---|
| `MODEL_PATH` | Original model checkpoint |
| `TRAIN_FILE`, `VALIDATION_FILE` | Prepared SFT JSON files |
| `OUTPUT_DIR` | Checkpoint output directory |
| `NPROC_PER_NODE` | Number of local training processes |
| `CUTOFF_LEN` | Tokenization cutoff |
| `GRADIENT_ACCUMULATION_STEPS` | Gradient accumulation count |
| `SAVE_STEPS`, `EVAL_STEPS` | Save and validation intervals |
| `SEED` | Training seed |

Run the appropriate entry point from the repository root:

```bash
# Qwen3.6-27B
bash magic_model_support/scripts/run_qwen_sft.sh

# Ministral-3-14B-Reasoning-2512, with its own model/data/output variables
bash magic_model_support/scripts/run_ministral_sft.sh
```

The launchers validate the prepared data before training. They do not generate or split the dataset. Exports are written to `checkpoint-<step>/hf_model`, and `latest_checkpoint.txt` identifies the latest export. The SFT exporter saves model weights for subsequent use; its training-state file explicitly marks exact SFT resume as unsupported.

See the [SFT guide](magic_model_support/WORKFLOWS.md#sft) for optional optimizer, batching, and checkpoint-retention settings.

## Alternating MAGIC training

Each trajectory contains an attacker rewrite followed by a defender response. VERL generates the active policy's trainable tokens and log probabilities. The frozen opponent and Qwen3Guard are called through OpenAI-compatible services. Training alternates fixed role blocks, starting with the defender; `TOTAL_MAGIC_STEPS` must be a positive multiple of `2 * SWITCH_FREQUENCY`.

Shared inputs include prepared MAGIC parquet files (`TRAIN_FILE`, `VAL_FILE`), a local `GUARD_MODEL`, `RUN_ROOT`, `RUN_ID`, `FORMAT_REWARD_VALUE`, `DATA_SEED`, and `ROLLOUT_SEED`. Configure model paths, GPU allocation, micro-batches, and service memory limits using the model-specific guides before running the commands below.

| Entry point | Additional setup | Detailed instructions |
|---|---|---|
| Qwen RL | `BASE_MULTIMODAL_MODEL`, `SFT_CHECKPOINT`, `VERL_SNAPSHOT_SOURCE`; two hosts sharing code, checkpoints, and `RUN_ROOT` | [Qwen RL](magic_model_support/WORKFLOWS.md#qwen-rl) |
| Ministral RL | `BASE_SOURCE_MODEL`, `SFT_CHECKPOINT_OVERRIDE` or `SFT_ROOT`, reasoning system prompt, and explicit GPU partitions | [Ministral RL](magic_model_support/WORKFLOWS.md#ministral-rl) |

```bash
# Qwen: run with the required environment on both hosts.
bash magic_model_support/scripts/run_qwen_rl.sh

# Ministral: run with the required environment on its dedicated host.
bash magic_model_support/scripts/run_ministral_rl.sh
```

The launchers use [`serve_magic_opponent.sh`](magic_model_support/scripts/serve_magic_opponent.sh) and [`serve_qwen3guard.sh`](magic_model_support/scripts/serve_qwen3guard.sh) to manage the required services. They merge the trained checkpoint at role boundaries and use the updated model as the next frozen opponent. The new AgentLoop implements a single attacker–defender game per trajectory; it does not expose all of the original separated trainer's multi-turn and metric-based switching options.

## Attacker format and reward behavior

The modern RL entry points include the invalid-rewrite handling from the original trainer, adapted to both model families:

1. **Validate complete, non-empty output.** Reasoning and answer content must both be non-empty. Required markers must appear exactly once and in order. Malformed or empty outputs receive the configured format penalty.
2. **Forward the visible attack.** Qwen forwards only `<answer>` content; Ministral forwards the answer after `[/THINK]`. Malformed tagged or empty attacker output falls back to the original question from `seed_prompt`, `question`, or `extra_info.raw_prompt`. Untagged direct answers may still be forwarded, but fail the attacker format check.
3. **Correct invalid task rewards within each group.** After gathering all rollout workers, `MagicGameAgentLoopManager` groups trajectories by the training `uid`. Before GRPO normalization, an invalid attacker's task reward is replaced with the mean of valid, scored attacks in that group. Its format penalty is then added.
4. **Keep penalties when no valid task score exists.** If the group has no usable valid attack, the replacement task reward is zero and the format penalty remains. Unscored trajectories do not contribute to the valid task-reward mean.

For example, with `FORMAT_REWARD_VALUE=0.5`, if all valid attacks in a group receive task reward `-1.5`, their total reward is `-1.0`. An invalid rewrite receives the same task baseline plus its format penalty, for a total of `-2.0`; breaking the format does not gain an advantage from a fixed zero task reward.

Both launchers already select the custom manager. Custom launch commands must also set:

```text
actor_rollout_ref.rollout.agent.agent_loop_manager_class=magic_model_support.rl.manager.MagicGameAgentLoopManager
```

See the [rollout guide](magic_model_support/WORKFLOWS.md#rollout-behavior) and [reward implementation](magic_model_support/rl/rewards.py) for details.

## Checkpoints and model compatibility

| Area | Behavior |
|---|---|
| Qwen checkpoint views | Text and service views reuse source weights through links. Keep the linked source checkpoints accessible throughout the run. |
| Ministral merged exports | The normalizer expects a single `model.safetensors` file and preserves the independent LM head. A missing head is rejected rather than reconstructed from embeddings. |
| RL checkpoint contents | Both launchers default to saving model weights only. Use `CHECKPOINT_SAVE_CONTENTS='["model","optimizer","extra"]'` from the start when optimizer and extra-state restoration is required, and choose matching load contents. |
| Role-boundary restart | Qwen uses `RESUME_RUN_ROOT` / `RESUME_MAGIC_STEP`; Ministral uses `RESUME_AFTER_MAGIC_STEP`. Follow each workflow's directory and checkpoint requirements. |
| Original training checkpoints | The modern entry points use different runtime APIs and checkpoint layouts. They are not a drop-in continuation of the original trainer's raw training state. |

Model loading support and training-state restoration are separate concerns. Consult the [checkpoint utilities](magic_model_support/README.md#qwen-checkpoint-views) and [training guide](magic_model_support/WORKFLOWS.md) before moving an existing experiment to the new entry points.

## Validation and evaluation

The format and reward regression tests can be run without launching model services:

```bash
python -m unittest -v \
  magic_model_support.tests.test_rl_rewards \
  magic_model_support.tests.test_agent_loop_rewards
```

These tests cover both output formats, seed fallback, group reward correction, and manager integration with stubbed service/backend boundaries. Terminal-token reward placement is tested with CPU tensors when PyTorch is available; those checks are skipped when it is absent. These are unit-level checks, not full distributed GPU training validation.

The model-support module provides training-service launchers, but no standalone benchmark or API-judge evaluation command. The repository's existing evaluation tools are described in [`eval/README.md`](eval/README.md).
